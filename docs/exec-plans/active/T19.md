## Frozen scope

Implement one canonical Helm deployment for the existing modular-monolith process boundaries,
with a low-cost k3s demo profile and a documented AWS EKS production reference. Consume the T18
image contract immutably, separate ConfigMap and Secret inputs, make a revision-scoped Job the sole
Alembic migration owner, preserve browser security and T17 telemetry, and provide bounded
install/validation guidance. Do not add microservices, live AWS infrastructure, application
business changes, migrations, T20 performance/DR work, or T21 final-hosted-gate work.

## Recovered assets and decisions

- ADR-015 freezes Docker Compose for local use, k3s plus Helm for the public demo, and AWS EKS with
  managed production dependencies as the reference architecture.
- ADR-016 freezes encrypted k3s secret handling and AWS Secrets Manager plus External Secrets as
  the production target. T18 intentionally did not publish from pull requests.
- No existing Helm chart, Kubernetes manifests, Terraform/CDK stack, or application deployment
  script exists. `deploy/` currently contains only the Keycloak demo realm.
- The Dockerfile produces one non-root image with OCI source/version/revision labels and includes
  the API, Celery, outbox, Alembic, static data, and built frontend artifacts.
- Current Compose process boundaries are API, tenant worker, maintenance worker, scheduler/Beat,
  and outbox relay. The accepted top-level architecture names API, Worker, Scheduler, and Outbox
  Relay; Helm will keep one worker Deployment with configurable queues/concurrency by default and
  will not add a separate domain service.
- `/health` checks PostgreSQL, Redis, and Qdrant but returns HTTP 200 with a `healthy` or `degraded`
  body and does not depend on an external model provider. Kubernetes API probes can therefore use
  `/health` without provider outages causing restarts; readiness requires a body-aware check or a
  dedicated application contract, so no business-code change will be made during this task.

## Implementation plan

1. Add one chart at `deploy/helm/star-warehouse-ai` with default, demo, and production-reference
   values plus a focused values schema.
2. Model API, worker, scheduler, outbox relay, migration Job, ConfigMap, Service, Ingress, service
   account, and optional production API PDB. Keep application images immutable outside explicit
   local/demo override and make digest take precedence.
3. Add conservative pod/container security, resources, lifecycle, checksums, labels, secret-key
   references, and private-registry support. Do not create RBAC or production Secret values.
4. Add bounded k3s deployment and static-validation scripts which never install k3s, rebuild an
   image, delete a namespace/PVC, or hide failures.
5. Document Helm/k3s operation, secret contract, migration/upgrade/rollback behavior, ingress and
   browser security, T18 artifact flow, observability integration, and AWS mapping.
6. Validate chart lint/template/schema/static security, scripts, OCI metadata, Alembic head, and
   disposable Kubernetes install/upgrade/rollback/failure behavior where the environment supports
   it. Record runtime limitations explicitly.

## Findings and execution notes

- No scope conflict was found. The repository's frozen deployment decisions align with the task.
- No application contract gap currently justifies changing business code. Probe implementation
  will use existing process and HTTP behavior and document its semantics.
- No pre-existing worktree changes were present at recovery.
- The canonical chart uses a normal revision-scoped migration Job rather than a pre-install hook.
  This lets the optional in-chart demo PostgreSQL become available on first install. Every
  application role has a non-mutating `alembic current --check-heads` init gate, while the Job is
  the only process that executes `alembic upgrade head` and provisions database roles.
- Runtime validation found and corrected Kubernetes-specific non-root details without application
  business changes: the application image needs explicit numeric UID/GID 999; demo PostgreSQL,
  Redis, RabbitMQ, and Qdrant need writable-path/cookie handling compatible with their upstream
  entrypoints; and runtime database logins need read-only access to `alembic_version` for the
  non-mutating init gate.
- A first missing-Secret injection also showed that changing the shared Secret reference replaced
  the demo StatefulSet pods. Demo infrastructure now has an explicit, separately configurable
  Secret reference, so an invalid application Secret fails the release while existing data
  dependencies and healthy application replicas remain available for atomic rollback.
