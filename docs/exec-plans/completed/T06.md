## Initial Findings

- `TenantScopedModel` and automatic ORM SELECT/write guards already exist, but there is no Tenant entity or status resolver.
- Request middleware and the tenant ContextVar implicitly fall back to `default`, allowing missing request identity to appear tenant-bound.

- Redis tenant caches use environment/tenant prefixes, while auto-heal cleanup still scans legacy `cache:*`, `rate_limit:*`, and `temp:*` patterns.
- Qdrant knowledge and memory writes/queries carry tenant payload/filtering, but filter construction is distributed and knowledge-vector deletion lacks a tenant-filtered seam.
- Knowledge synchronization launches a subprocess without TaskContext propagation, causing vector writes to depend on the legacy implicit default.
- No S3/object-storage Port is active. Knowledge uploads use a local filesystem compatibility path and require tenant namespacing; the object-storage row in the resource inventory will remain `NOT CURRENTLY ACTIVE`.

## FIX-TX Ownership Trace Before Repair - 2026-09-12

- The registration route has no explicit transaction boundary. `TenantResolver.resolve()` performs the first database query and implicitly starts the request session transaction.
- `AuthService.register_user()` conditionally owns transactions: it opens a transaction only when none exists, but otherwise performs `flush()` and `refresh()` without committing. On the real route, the resolver-created transaction always selects the flush-only path.
- `get_session()` only yields and closes the `AsyncSession`; it does not commit after the route. Consequently, the route can construct and return a token response while the inserted user remains uncommitted and is rolled back when the session closes.
- Repair direction: make the registration application route the single transaction owner; keep the service as a nested add/query/flush collaborator; leave repositories and the global session dependency free of hidden commits.
