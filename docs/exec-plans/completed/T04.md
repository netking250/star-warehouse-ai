# T04 — RabbitMQ + Reliable Celery

## Objective

Make RabbitMQ the Celery broker and provide duplicate-safe, crash-recoverable execution for protected critical handlers through persistent receipts, bounded retry classification, and a real RabbitMQ dead-letter path. Global exactly-once is not claimed.

- The worktree contains overlapping uncommitted T00–T03 changes; preserve them without reset, stash, or broad commit.
- Installed versions: Celery `5.6.3`, Kombu `5.6.2`.
- T05 remains `NOT_STARTED`; memory consistency is excluded.

## Required Semantics

- Database business state plus outbox intent remains atomic.
- Outbox to RabbitMQ remains at-least-once.
- Protected critical consumers use stable tenant/task/idempotency identity and suppress completed duplicates.
- Stale processing claims are recoverable; a committed `PROCESSING` receipt never becomes a permanent poison lock.
- Transient failures retry with bounded exponential backoff and jitter; permanent or exhausted failures are explicitly dead-lettered.
- Global exactly-once is not claimed, especially for external providers that do not honor idempotency keys.

## Behavior-First Plan

1. Duplicate delivery of one critical refund envelope produces one database business effect and a completed receipt.
2. A stale processing receipt can be reclaimed safely after worker loss.
3. A transient failure retries and later succeeds without dead-lettering.
4. Exhausted transient and permanent failures retain sanitized identity and failure metadata in the RabbitMQ DLQ.
5. RabbitMQ routes critical/default/system workloads correctly with late ACK and worker-loss redelivery policy on protected tasks.
6. A real broker smoke proves Outbox → RabbitMQ → Celery Worker → protected handler; fault injection proves redelivery and DLQ routing.
7. A new additive receipt migration upgrades a fresh database to one head.
8. Run targeted/integration, quality, full backend coverage, documentation, and state gates; leave T04 at `AWAITING_ACCEPTANCE`.

## Findings

- T03's `TaskPublisher` seam already isolates services from broker selection; only Celery composition/configuration changes for RabbitMQ.
- Existing critical refund tasks commit inside handler bodies and have no receipt seam; payment and admin-notification database effects need transaction ownership moved behind protected execution.
- Existing Compose uses Redis as both broker and result backend and has no RabbitMQ service or relay runtime.
- Every configured Beat entry now supplies an explicit `SystemTaskEnvelope`; compatibility wrappers validate and bind it while retaining direct in-process test calls without inventing a tenant.

## Implemented Semantics

- RabbitMQ is the Celery broker; Redis may remain a result backend but is not the broker.
- Protected database-local refund effects and their `COMPLETED` receipt share one PostgreSQL transaction and stable `(tenant, handler, idempotency key)` identity.
- Critical refund tasks use late acknowledgement, worker-loss rejection/redelivery, disabled failure/timeout acknowledgement, prefetch one, and bounded classified retry.
- Exhausted/permanent failures publish sanitized terminal evidence to a real RabbitMQ DLQ; a DLQ publish failure rejects and requeues the original delivery.
- Outbox publication remains at-least-once. Protected handlers are duplicate-safe; global exactly-once is not claimed, especially for providers without idempotency support.
