seam while preserving T08 identity, T06/T07 tenancy/RLS, and T10 browser transport boundaries.

## Initial Authorization Inventory

### EXISTING_AND_REUSABLE

- Tenant-owned `User` holds the current local role, `is_admin`, and `is_active` state.
- `Role`, role-to-scope mapping, signed application JWTs, Redis token/session revocation, trusted
  `TenantContext`, request RLS binding, and FastAPI dependencies already exist.
- Local and OIDC login both resolve the same local `User` and issue the same application JWT.
- Tenant-owned audit tables and correlated logging infrastructure exist, but the current human
  review audit schema is not suitable for authorization mutations.

### NEEDS_CONSOLIDATION

- JWT role/scope claims are currently used directly as effective authority and can remain stale.
- HTTP authorization is split between authenticated-user dependencies and coarse
  `SUPER_ADMIN` checks; WebSocket helpers repeat token/tenant/admin logic.
- Route classification is implicit and has no complete deny-by-default inventory guard.
- Admin capabilities need read/manage separation and sensitive review mutations need stronger
  scopes than read operations.

### LEGACY

- Colon-delimited scope strings and `get_admin_user_id` are compatibility surfaces.
- `User.is_admin` plus `User.role` is a dual representation of application role.
- WebSocket query-token transport remains temporarily compatible and is owned by T10.

### MISSING

- A normalized policy decision/reason model and authoritative current-state resolver.
- Explicit production HTTP/WebSocket route classification with a failing unclassified-route guard.
- Minimal authorization-management API, privilege-escalation/last-admin guards, and atomic
  authorization mutation audit evidence.
- Focused authorization architecture documentation and T09 targeted tests.

## Implementation Plan

1. Establish `app.authorization` as the canonical role, capability, context, decision, and route
   policy seam; retain narrow compatibility re-exports from `app.core.security`.
2. Resolve effective authority from the active tenant-owned `User` record on every protected
   request and WebSocket connection; JWT authorization snapshots remain non-authoritative.
3. Replace coarse route checks with capability dependencies and classify every HTTP/WebSocket or
   explicit infrastructure/public endpoint in a structural inventory.
4. Add minimal role/status administration with explicit `identity.manage`, no self-elevation,
   last-admin protection, and authorization audit rows in the caller-owned transaction.
5. Add an additive migration only if the focused authorization audit model requires it, preserving
   all users and the accepted migration history.
6. Run only targeted T09 tests plus scoped Ruff, format check, ty, and Alembic single-head checks.

## IMPLEMENT-stage Constraints

- Do not run the complete backend or frontend suite.
- Do not start T10 or T11.
- On passing targeted gates, retain `T09 = IN_PROGRESS` and set
  `execution_stage = VERIFY_PENDING`.

## Implementation Result

- `app.authorization.policy` is authoritative for application roles, dotted capability scopes,
  current tenant authorization context, decisions, and reason codes.
- The existing tenant-owned active `User` is the membership/source of truth. JWT role/scope claims
  remain compatibility snapshots and upstream OIDC role/group claims are not trusted.
- Every protected HTTP request and both WebSocket paths reload current membership/role state from
  PostgreSQL; no authorization cache was added, so role and membership revocation are immediate.
- The route inventory classifies 120 HTTP method/routes, 2 WebSocket routes, and 4 mounts. Startup
  and tests fail on unknown routes, and protected HTTP routes must contain the canonical dependency.
- Admin routes use route-specific capability policy through the compatibility adapter instead of a
  blanket `SUPER_ADMIN` route check. Sensitive mutation capabilities are separate from reads.
- Minimal membership read/role/status APIs require `identity.read`/`identity.manage`, apply explicit
  tenant predicates, prevent self-change and unauthorized super-role grants, and protect the final
  active tenant administrator.
- Authorization mutations and `authorization_audit_events` evidence share one caller-owned
  transaction. The additive table has forced RLS under the existing T07 capability roles.
- Focused architecture documentation is in `docs/architecture/AUTHORIZATION.md`.
