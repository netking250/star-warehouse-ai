## Canonical Terminology

Canonical execution identity is `tenant_id + conversation_id + turn_id + run_id`, with
`correlation_id` for tracing and a tenant-and-conversation-scoped client `idempotency_key` for
logical submission identity. `thread_id` remains the transport/checkpoint compatibility name and
maps to canonical `conversation_id`; it is not a run or turn identifier.

| Existing concept | Classification | T12 decision |
| --- | --- | --- |
| `MessageCard` | EXTEND | Add nullable conversation/turn/run/logical IDs and reuse it for the durable user and terminal assistant messages. |
| client `thread_id` | LEGACY | Preserve the accepted tenant/user-prefixed value as canonical `conversation_id` at the transport boundary. |
| RedisVL / optimized checkpointer | REUSE | Keep as executor acceleration/transient graph state under a run-isolated namespace; never use it as durable runtime truth. |
| `GraphExecutionLog` / `GraphNodeLog` | LEGACY | Preserve as observability projections; they are not execution lifecycle authority. |
| `ReviewTicket` / refund `AuditLog` | REUSE | Preserve existing after-run risk review and refund decision workflows; neither is a LangGraph interrupt/resume primitive. |
| synchronous agent tools | REUSE | Leave existing execution unchanged; provide a durable async tool identity/result-acceptance boundary without converting tools. |
| SSE token and metadata events | EXTEND | Normalize them behind runtime/executor contracts; token chunks remain transient. |
| Conversation / Turn / Run / ordered lifecycle events | MISSING | Add the minimum PostgreSQL-authoritative tenant-owned models and runtime service. |

AI human-review pause/resume is `N/A` for T12 runtime integration: repository graph sources contain

## Behavior-First Plan

1. Inventory conversation/message/thread/run/checkpoint/review/tool/event concepts and select the
   smallest compatible durable model.
2. Add a centralized runtime state machine and prove legal, illegal, terminal, cancellation, and
   terminal-response uniqueness behavior through the runtime interface.
3. Add PostgreSQL-backed idempotent submission and per-conversation serialization that works across
   workers while allowing different conversations to proceed independently.
4. Add revision-checked cancellation and async tool/human result acceptance so stale, duplicate,
   wrong-run, and cross-tenant inputs cannot mutate current state.
5. Add monotonic durable lifecycle events, replay/final-result recovery, orphan reconciliation,
   and coherent acceptance/completion transactions.
6. Add a `ConversationExecutor` seam and LangGraph adapter; migrate chat transport without exposing
   graph internals or changing T10 transport behavior.
7. Add the minimum additive migration, forced RLS, T11 classification, T09 route classification,
   scoped guidance, and targeted compatibility/integration evidence.
8. Run only T12-targeted pytest groups, scoped Ruff/format/ty, Alembic heads, and focused migration
   checks; leave T12 `IN_PROGRESS / VERIFY_PENDING` and T13 `NOT_STARTED`.

## Constraints

- PostgreSQL is authoritative; Redis/checkpoints are acceleration or resumable executor state only.
- Same-conversation mutating turns are serialized; this must not serialize different conversations.
- Cancellation is logically authoritative even when provider/tool work cannot be physically stopped.
- Infrastructure remains at-least-once while logical terminal outcomes are idempotent; global
  exactly-once execution is not claimed.
- T13 provider routing and T14 retry/fallback policy are explicitly excluded.

## Execution Notes

- Targeted verbose output belongs outside the repository.
- Accepted Alembic head at start is `d8e9f0a1b2c3`; historical migrations are immutable.
- Same-conversation semantics are an explicit `409` conflict while a non-terminal mutating run is
  active. PostgreSQL transaction-scoped advisory locks serialize this decision across workers;
  locks release automatically at transaction end, while different conversation keys remain
  parallel.
- State transitions are centralized as `PENDING`, `RUNNING`, `WAITING_TOOL`, `WAITING_HUMAN`,
  `COMPLETED`, `FAILED`, and `CANCELLED`; terminal states cannot reopen.
- Cancellation is logically authoritative. It cannot promise provider/process interruption, but
  completion and tool-result acceptance check durable run state/identity/revision and reject late
  results.
- `TURN_ACCEPTED`, run/tool lifecycle, cancellation, failure, stale-result, and terminal events are
  durable and sequence-ordered per run. High-frequency token chunks are intentionally ephemeral;
  reconnect recovers durable status, lifecycle events, and the terminal `MessageCard` result.
- Orphan reconciliation is bounded by tenant, user, age threshold, and batch limit; it marks stale
  non-terminal work `FAILED / ORPHANED_RUN` without invoking T14 retry policy.
- Existing graph tools are synchronous, so T12 performs no new background tool publication and no
  runtime transaction requires an Outbox event. Existing T03/T04 protected async business paths
  are unchanged; the async tool acceptance seam propagates trusted `TaskContext` for a future
  caller that atomically dispatches work.
- Additive migration `e9f0a1b2c3d4` follows accepted head `d8e9f0a1b2c3`, adds five tenant-owned
  runtime tables and nullable `MessageCard` identity columns, applies forced RLS with `USING` and
  `WITH CHECK`, and registers every dataset with T11 classification/retention policy.
