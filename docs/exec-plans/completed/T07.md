## Initial Findings

- `TenantContext` is the sole trusted application identity and already fails closed when missing.
- Async and sync SQLAlchemy sessions share global ORM read/write guards, but no PostgreSQL
  transaction-local tenant setting is currently bound.
- API, worker, migrations, and operational processes currently derive connections from one
  PostgreSQL credential set; local runtime commonly connects as `postgres`, which bypasses RLS.
- Tenant resolution may start a transaction before `TenantContext` is bound, so database binding
  must refresh centrally when a resolved context becomes available in the same transaction.
- Outbox relay and scheduled system tasks legitimately scan across tenants. They require an
  explicitly separate maintenance database capability; normal API/tenant worker sessions must
  never inherit it.

## Behavior-First Plan

1. Add one canonical transaction-local setting, `app.current_tenant_id`, and central SQLAlchemy
   binding for async and sync sessions.
2. Add a new additive migration after `f4a5b6c7d8e9` that creates non-login runtime/maintenance
   capability roles, enables and forces RLS, and applies `USING` plus `WITH CHECK` policies to the
   exact T06 inventory.
3. Provision separate least-privilege login roles from configured secrets, keep Alembic on the
   migration/admin URL, and isolate maintenance processes from API/tenant workers.
4. Prove raw read, direct-ID read/update/delete, insert rejection, missing-context behavior,
   connection-pool isolation, worker propagation, runtime-role reality, and catalog inventory on
   a temporary real PostgreSQL database migrated to head.
5. Re-run existing T06 application guard tests plus scoped Ruff, format check, ty, Alembic heads,
   migration import, and escape-hatch audit only.

## Implementation Delivered

- `app.current_tenant_id` is the sole PostgreSQL tenant setting and is bound with transaction-local
  `set_config(..., true)` by centralized SQLAlchemy session events for both async API and sync worker
  sessions; the existing T06 `TenantContext` remains the trusted source.
- Migration `a5b6c7d8e9f0` applies forced RLS and one structural `ALL` policy with `USING` and `WITH
  CHECK` to the exact 39-table T06 inventory. It fails if an inventory table is absent or either
  fixed capability role can reach another role.
- Runtime and maintenance are fixed non-login, non-inheriting, non-bypass capability roles. Login
  roles are provisioned from configured secrets, rejected when privileged or unexpectedly enrolled,
  and kept distinct from the Alembic/admin URL.
- Normal API and tenant workers use runtime capability. Outbox and explicitly routed scheduled
  system work use an independent maintenance process/login; maintenance is globally scoped only
  when no tenant is bound and becomes tenant-scoped when a valid context exists.
- T06 ORM predicates, write validation, relationship guards, tenant status behavior, and external
  namespace isolation remain intact. No tenant identifier, uniqueness, index, or business-data
  redesign was introduced.

## T07-FIX-RLS-CONCURRENCY - Completion Evidence

Completed: 2026-09-13

Status: `BLOCKED`

Execution Stage: `VERIFY_PENDING`

Exact race:

- Classification: combination of **A + B**, not C. `build_memory_node` passed one `AsyncSession`
  to four independent structured-memory reads launched by `asyncio.gather`; their first ORM
  executions concurrently entered `_refresh_database_tenant_context` while that session was
  provisioning its connection/transaction, which SQLAlchemy explicitly forbids.
- The refresh hook is evaluated before every ORM operation, but after a transaction has a stable
  tenant its `session.info` guard prevents repeated tenant-binding SQL. Production workflow
  construction does not inject a session, so no Conversation Runtime redesign or T12 work was
  required.

Implementation:

- Concurrent structured-memory reads now each own an independent `AsyncSession` and explicit
  transaction. The trusted tenant ContextVar propagates into each task; `after_begin` binds
  `SET LOCAL app.current_tenant_id` for that transaction, and session exit removes the context.
- `_refresh_database_tenant_context` no longer provisions a connection when no transaction exists;
  it remains available only to rebind an already-active transaction after trusted tenant resolution.
- The explicit caller-owned session compatibility seam performs ordered reads inside that caller's
  transaction and is never shared across `asyncio.gather`. No global lock, retry, sleep, default
  tenant, maintenance credential, RLS bypass, or memory-consistency redesign was introduced.

Targeted verification:

- Original graph memory integration node plus independent-session ownership regression: `2 passed`.
- Disposable real-PostgreSQL targeted set: `5 passed` — eight concurrent same-tenant structured
  reads, concurrent Tenant A/B structured reads, pooled A -> B -> no-context reuse, raw unfiltered
  RLS isolation, and worker TaskContext propagation.
- Both concurrency tests observed `star_warehouse_runtime` as `current_user`; maintenance
  credentials were not used, and Tenant A/B facts remained isolated.
- Scoped Ruff, Ruff format check, and ty `--error-on-warning` passed for all changed Python files.
- The unrelated performance timing test was not modified or run. The full backend suite was not run.

State transition:
