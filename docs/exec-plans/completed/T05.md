# T05 — Memory Consistency

## Objective

Make PostgreSQL the authoritative memory store and Qdrant a recoverable derived vector index. A caller-owned database transaction persists structured memory plus a minimal vector-sync outbox event; reliable consumers project committed state into Qdrant after commit.

## Recovery Evidence

- External gate: `T04 = PASS` received on 2026-09-12.
- Branch: `main`; recovery HEAD: `bf0d5b9`.
- The worktree contains overlapping uncommitted T00–T04 changes; preserve them without reset, stash, or broad commit.
- T06 remains `NOT_STARTED`.

## Required Semantics

- PostgreSQL is authoritative; Qdrant is derived and never participates in the database transaction.
- Structured memory plus vector-sync intent share one caller-owned transaction.
- Vector events carry identity/version/operation only, never full memory text.
- Stable point identity makes duplicate deliveries safe; an older version cannot overwrite a newer indexed version.
- Delete intent survives Qdrant failure and retries; reconciliation detects and enqueues version drift.
- Vector read failure produces an explicit degraded outcome while structured memory remains valid.
- No 2PC, event sourcing, LangGraph rewrite, T06 work, or global exactly-once claim.

## Behavior-First Plan

1. Commit a memory command, close session 1, and retrieve it through session 2 together with its pending outbox event.
2. Roll back a memory command and prove neither PostgreSQL memory nor outbox intent exists and no vector call occurred.
3. Consume a minimal vector-sync event; Qdrant failure remains retryable and later recovery succeeds.
4. Deliver duplicate and stale events and prove one logical latest vector state.
5. Tombstone/delete authoritative memory plus delete intent, then recover a failed Qdrant deletion.
6. Prove tenant isolation and a reconciliation/degraded-read seam.
7. Run targeted and full verification gates; leave `IN_PROGRESS` with `execution_stage: EXTERNAL_ACCEPTANCE_PENDING` until external acceptance.

## Initial Findings

- `StructuredMemoryManager.save_interaction_summary` and `save_user_fact` only flush/refresh; callers can incorrectly treat the returned row as committed.
- `SessionSummarizer.run` directly upserts Qdrant after the PostgreSQL flush, so a later session rollback can leave an orphaned vector.
- `VectorMemoryManager.upsert_message` creates a random point ID on every call, so retries create duplicate logical vectors.
- Current memory models do not carry an authoritative revision or tombstone state, and there is no minimal vector-sync command payload or reconciliation seam.

## Implementation

- Added `InteractionSummary.version`, `is_deleted`, and `deleted_at` through additive revision `e3f4a5b6c7d8`.
- `StructuredMemoryManager` now enqueues PII-free `memory.sync_vector` upsert/delete intent in the same caller-owned transaction as the authoritative row or tombstone.
- `SessionSummarizer` owns the single commit/rollback boundary and no longer calls Qdrant directly.
- The reliable Celery handler reuses T04 task receipts with a committed, recoverable external-operation lease and bounded retry/DLQ policy.
- Qdrant projection uses a stable tenant + memory ID point, loads text from PostgreSQL, ignores stale versions, and makes duplicate upsert/delete execution logically idempotent.
- Tenant-scoped reconciliation enqueues drift repair, and memory reads retain structured state while reporting `vector_recall_degraded`.
