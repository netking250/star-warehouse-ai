# T13 - Dynamic Model Gateway

## Objective

Create one provider-neutral model gateway seam for current remote chat-model usage. Resolve
configuration-driven use-case routes into explicit ordered candidates, invoke exactly one selected
candidate, normalize responses/streaming/tool calls/errors, and keep OpenAI, DashScope, and Mock
provider details below the adapter interface.

## Interface and Seam

- `ModelGateway` is the deep module consumed by application code.
- A normalized request/response/stream interface hides provider SDK objects and validates required
  capabilities before I/O.
- `ProviderAdapter` is the external-service seam with OpenAI, DashScope, and deterministic Mock
  adapters.
- Route resolution returns ordered candidates explicitly. Invocation accepts one candidate; it does
  not retry or fail over. T14 exclusively owns retry, circuit, fallback, and degradation policy.

## Constraints

- OpenAI is the primary configured candidate and DashScope is the ordered alternate where required
  capabilities are supported.
- Provider base URLs and credentials come only from trusted server settings; ordinary requests
  cannot select providers, models, or endpoints.
- Real adapters use explicit bounded timeouts and disable SDK automatic retries.
- Do not log prompts, responses, tool arguments, credentials, authorization headers, or raw
  provider payloads by default.
- Do not add persistence or a migration unless repository inspection proves it necessary.
- Do not run the complete backend suite and do not start T14.
