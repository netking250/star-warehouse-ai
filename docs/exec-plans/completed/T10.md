# T10 - Secure Browser Session

## Objective

Move browser authentication credential transport from JavaScript-readable token handling to one
canonical HttpOnly cookie with session-bound CSRF, exact Origin validation, logout revocation, and
cookie-authenticated WebSocket handshakes, while preserving the accepted T08 identity, T09
authorization, and non-browser Bearer-token compatibility.

## Behavior-First Plan

1. Inventory every browser credential storage/transmission path, current JWT lifetime/revocation,
   OIDC callback, logout, CORS, route inventory, HTTP client, auth store, and WebSocket handshake.
2. Add explicit production-secure cookie and trusted-origin/CSRF settings; keep local HTTP relaxation
   explicit and align cookie lifetime with the existing application JWT.
3. Normalize Bearer and cookie credentials into the existing principal with deterministic ambiguous
   credential handling, then enforce session-bound CSRF and exact Origin/Referer validation only for
   unsafe cookie-authenticated requests.
4. Set/rotate the browser cookie on local and OIDC login, expose authenticated CSRF bootstrap,
   revoke and clear on protected POST logout, and classify every new/changed route in T09 inventory.
5. Authenticate browser WebSockets from the HttpOnly cookie, reject query credentials, validate
   Origin, and continue applying T09 current-state authorization before accept.
6. Remove frontend JWT persistence and token-bearing HTTP/WebSocket construction; bootstrap identity
   from the server, send cookies, keep CSRF in memory, and make logout server-authoritative.
7. Add focused backend, WebSocket, frontend, and browser tests plus static secret scans and scoped
   quality/Alembic checks; do not run the full backend suite or start T11.

## Initial Findings

- The frontend persisted the application JWT in Zustand `auth-storage` backed by localStorage,
  rebuilt `Authorization: Bearer` from that state, and appended it to WebSocket query strings.
- The backend accepted WebSocket query-token authentication; local login returned the application
  JWT, and OIDC callback completion returned it in JSON instead of establishing a browser cookie.
- The existing application credential is a 30-minute JWT with `jti`/session identifiers and Redis
  revocation; no refresh-token or independent browser-session framework exists.
- CORS already used explicit origins with credentials but wildcard methods/headers; request logging
  redacted query tokens but did not consistently redact structured/raw credential headers.
- T09 already reloads current tenant membership and role state for every protected HTTP request and
  WebSocket handshake, so cookie transport can reuse that seam without snapshot authorization.

## Implementation Result

- Added one host-only HttpOnly application-token cookie with production `Secure=true`, explicit
  `SameSite=Lax`, `Path=/`, and expiry/max-age bounded by the existing JWT lifetime; explicit HTTP
  development may set Secure false, while insecure production and insecure SameSite=None fail
  settings validation.
- Added signed random CSRF tokens bound to JWT `jti`, login session ID, and expiry; unsafe
  cookie-authenticated requests require the in-memory token and exact configured Origin, with exact
  Referer fallback only when Origin is absent.
- Bearer-only clients remain CSRF-free and use the same principal; conflicting Cookie/Bearer
  credentials are rejected, while duplicate credentials remain subject to cookie CSRF controls.
- Local browser login and OIDC completion issue fresh application credentials, rotate a valid prior
  browser credential, set the cookie, and never expose the application token to browser JavaScript
  or redirect URLs.
- POST logout revokes the current token in the existing Redis revocation store before clearing the
  cookie; stale copies and old CSRF state are unusable.
- Browser WebSockets authenticate from the HttpOnly cookie with exact Origin and T09 authorization;
  non-browser Authorization headers remain supported, while `token`/`access_token` query parameters
  are rejected.
- Frontend auth state is server-bootstrapped from `/me`, credential transport uses
  `credentials: include`, CSRF lives only in module memory, the known legacy `auth-storage` key is
  deleted without touching preferences, and WebSocket URLs contain no credential.
- Structured and raw request credential fields are redacted from logging, and T09 inventory now
  explicitly classifies both new browser-session routes.
